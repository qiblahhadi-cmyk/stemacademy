# Administrator Account Provisioning — Phase 6

**Status: Staging and first-password workflow implemented; emulator/production operator verification remains outstanding.**

## Trust boundaries

- Firebase Auth UID identifies the login account; it is not the permanent academy ID.
- Permanent student/staff academy IDs are allocated server-side and immutable.
- The trusted `users/{uid}` document determines role and active status.
- Firebase Admin credentials remain server-side or in a separately controlled owner/technical-custodian shell; they are never sent to the browser or ordinary administrators.
- Passwords and reset tokens are never stored in Firestore, audit metadata, source code or generated files.
- No public self-registration or client-selected role/ID exists.
- `stemacademy.edu.pk` is an internal alias direction only, not a deliverable email address.

## 1. Administrator account staging

`POST /api/admin/accounts` is available only after Firebase ID-token verification and a server-side `users/{uid}` role check for `admin`. It accepts exactly `role` (`student` or `teacher`) and `displayName`. The client cannot choose a Firebase UID, academy ID, alias, password or privileged role.

The server:

1. Allocates a permanent ID using the existing transactional counter (`SA-YYYY-NNN` for students; `SA-TCH-NNN` for teachers). Numbers are never reused; gaps after failed provisioning are acceptable.
2. Derives the internal Firebase alias using the existing `academyIdToAuthEmail` helper.
3. Creates the Firebase Auth user with `disabled: true` and no password.
4. Writes `users/{uid}` with `active: false` and `provisioningStatus: "pending_activation"`.
5. Writes an audit event containing role and academy ID, but no credential.
6. Deletes the Auth user if profile persistence fails. If compensating deletion fails, the disabled orphan requires operator review.

The response contains UID, academy ID, role and pending/disabled status only. It never contains a password or reset link.

## 2. Owner-verified initial credential handoff

A no-cost, in-person handoff avoids dependence on email/SMS/WhatsApp delivery. The initial credential is generated by the owner/technical custodian in a controlled local shell, after the designated academy authority has verified the person's identity in person. The person receives the temporary password privately and must immediately replace it in the LMS.

The `scripts/issue-initial-credential.mjs` utility:

- Requires a pending, inactive student or teacher profile and a corresponding disabled Firebase Auth user with no outstanding `mustChangePassword` claim.
- Requires the operator to identify an active administrator UID in the same Firestore project.
- Requires `ACCOUNT_ACTIVATION_VERIFIED=true`, set only after the in-person identity check.
- For non-emulator execution, requires `ALLOW_OWNER_ACCOUNT_ACTIVATION=true`, server-only Firebase Admin credentials, and an exact match between `FIREBASE_ADMIN_PROJECT_ID` and `ACCOUNT_ACTIVATION_EXPECTED_PROJECT_ID`. It refuses to run inside Netlify.
- Generates a cryptographically random temporary password, enables the Auth account, and sets the custom claim `mustChangePassword: true`.
- Acquires a transactional one-time `credential_issuing` state before changing Auth, then transitions to `credential_issued` only after the temporary password and forced-change claim are set. This prevents two operators from issuing competing initial credentials concurrently.
- Records the operator, target academy ID and timestamp, but never records the temporary password.
- Displays the temporary password once in the local terminal. Never redirect output, save a transcript, paste it into chat, email it, or write it to a file. Perform the handoff privately and in person.
- If the process is interrupted after the `credential_issuing` lock is acquired, the account remains unusable. Do not blindly rerun the script: the owner/technical custodian must inspect Auth and Firestore state and perform a documented manual recovery before returning the profile to `pending_activation`.

Example for the synthetic emulator only:

```bash
ACCOUNT_ACTIVATION_OPERATOR_UID=<synthetic-admin-uid> \
ACCOUNT_ACTIVATION_VERIFIED=true \
npm run issue-initial-credential:emulator -- <pending-user-uid>
```

A controlled owner/technical-custodian shell can use `npm run issue-initial-credential -- <pending-user-uid>` only after the separate in-person verification and project-confirmation gates are satisfied. **Do not run this against a production project in this Phase 6 environment.** Production Firebase has not been connected or tested.

## 3. Forced first-password change

- The owner-issued custom claim `mustChangePassword: true` is verified from the Firebase ID token.
- While the claim is present, server middleware rejects ordinary API routes. Only `/api/me` and `/api/auth/complete-password-change` are allowed for the pending account.
- The session bootstrap redirects the user to `/activate-account.html`.
- The user chooses a password of 12–128 characters. The authenticated HTTPS endpoint uses Firebase Admin SDK to update the password; it does not write the password to Firestore or audit logs.
- The server marks the profile active and `provisioningStatus: "active"`, then clears `mustChangePassword` while preserving unrelated custom claims.
- If claim clearing fails, the token remains restricted and the user can retry the change flow. A deactivated profile cannot use the bootstrap path to reactivate itself.
- Audit records contain only the account UID, academy ID, role and timestamps.

## 4. Deactivation and immutable identifiers

- Deactivating a student/teacher sets the trusted profile `active: false` and attempts to disable Firebase Auth. Server middleware rejects inactive profiles even if Auth disablement needs manual follow-up.
- `academyId` and `role` are not accepted by update routes.
- Pending accounts cannot be activated through ordinary profile editing.
- Re-enabling a previously active account is an explicit administrator action and synchronizes Firebase Auth disabled state.

## 5. First administrator and recovery

The ordinary administrator endpoint cannot create an administrator. The first administrator must be bootstrapped by the academy owner/designated authority using a separate controlled procedure. Administrator recovery follows the owner-verified procedure documented in `FIRESTORE_DATA_MODEL.md`. The academy must not depend on the only administrator account for Firebase project ownership.

## 6. Zero-budget assessment and remaining gates

This design uses existing Firebase Auth, Firestore, Firebase Admin SDK and a controlled in-person handoff; it introduces no paid messaging or new backend service. It does require a trusted owner/technical custodian with separately protected Firebase Admin credentials. Ordinary administrators never receive those credentials.

Before real accounts are created, verify with synthetic accounts in Auth/Firestore emulators:

1. Alias acceptance and sign-in for `stemacademy.edu.pk`.
2. Disabled account cannot sign in before credential issuance; interrupted `credential_issuing` state remains locked and requires operator recovery.
3. Only the owner-verified operator script can issue a temporary credential and set the must-change claim.
4. A must-change account cannot call normal API endpoints.
5. First-password change updates Auth, activates the profile and clears the claim.
6. Failed claim clearing remains safely restricted and is retryable.
7. Deactivation during the password-change process cannot reactivate the profile.
8. Duplicate alias, partial failure and orphaned disabled Auth-account recovery.
9. No password or reset token appears in logs, Firestore, audit events or API responses.

Production use remains blocked until the same controlled handoff is rehearsed with the academy owner/technical custodian, emulator tests pass, and production Firebase configuration is separately authorized. No production project has been accessed in this Phase 6 work.
